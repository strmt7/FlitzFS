## Controlled experiment

The explicit retirement-reference workflow has two independent disposable
Windows VM jobs, named windows-mount: held and closed. Each runs exactly once.
A CPU-only source-transformation test precedes them. All thirteen ordinary core
jobs must have passed for the exact control commit; the gate retains their actual
run/job identities before driver provisioning. Every existing workflow is unchanged.
Each VM first runs the current read-only mount/recovery probe and strict report
reconciliation. An incomplete prerequisite prevents the reference trial.

Preparation verifies exact Git roots, revisions, tracked cleanliness, disabled Git
replacements, canonical historical source/CMake/build/supervisor blobs, the
qualified current controller-budget header and identical SDK locks. Files must
be regular, single-link and bounded. A NEW private generated source, CMake wrapper
and build script leave original tracked bytes untouched. Only that private source
is compiled into the historical test target; no product target consumes it.

Both variants use the same diagnostic controller, original 15-second source
deadline and original two-second termination observation. The common controller
has 128-MiB per-process/256-MiB aggregate, two-process,20%-CPU,below-normal,
ten-user-CPU-second and verified-headroom limits. The source retains its old
128-MiB/one-process/20%-CPU creation-time child job and original trusted fixture.

The held variant leaves the acknowledged client handle live. The closed variant
checks real CloseHandle success, invalidates its owner, and requires zero contexts
while the dispatcher stays healthy. Context drain has a maximum two-second bound
INSIDE the unchanged 15-second operation deadline. No stop/unmount is requested.
Both write a NEW <=256-byte flushed phase receipt after the original acknowledgement,
binding variant, source PID and observed context count. This uses the second
allowed bounded report slot; no continuation or verifier report is written.
The image remains <=4 MiB and aggregate reports <=4096 bytes.

The common controller never calls the historical multi-profile entrypoint.
There is no resumer, replacement, remount or second trial. It retains the exact
process-object lease. Only confirmed timeout retirement permits phase-receipt
comparison, original acknowledgement emission, mount-absence inspection and
independent CPU verification of all native records and the exact 7001 sample bytes.
Unknown retirement is terminal and returns failure before any backing access.

## Interpretation

This is an instrumented reconstruction, not an untouched historical binary.
Common instrumentation and current Windows/toolchain state may change timing.
One trial per variant cannot estimate an intermittent failure rate. Both passing
would be inconclusive. A differing result would test the held-handle hypothesis
under the captured VM conditions; it would not reconstruct the older kernel state
or prove that every future failure shares that cause. Preserve original failures,
all ordinary current regression gates, and D01 uncertainty until evidence warrants
a narrower supported conclusion. No timer increase can count as a repair.

Current Microsoft API captures on13 November2026 retain the distinction between
a termination request and observed process exit: pending I/O can delay exit, and
job termination applies process termination to each member. The process page
reports a2026 update; the job page retains older publisher metadata. These are
currently served API contracts, not newly published2026 features.
See evidence/retirement-research-b2cf989.json for native provider receipts and
digests. The exact pinned WinFsp StopDispatcher implementation has an infinite
thread join during ordered shutdown; forced process termination bypasses normal
C++ destruction. Its source does not establish the cause of this old failure.

No owner experiment, driver change, persistent task, automatic GPU operation,
resident worker or useful compression/performance qualification follows.
