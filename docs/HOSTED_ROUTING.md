# Isolated source routing and AMD deployment research

The owner requires CocoIndex Code before broad repository navigation and reviewed
Crawl4AI captures for web-page content. These development tools execute only on
disposable hosted VMs. They are never dependencies of the filesystem executable,
its CPU recovery path, mounted callbacks or an end-user installer.

## Source-bound semantic routing

hosted_semantic.py provisions the official CocoIndex Code 0.2.43 wheel with exact
size/SHA-256 verification into a fresh private venv. Native pip resolver reports
select compatible binary wheels; each selected wheel is separately downloaded,
hashed and inspected before an offline hash-required installation. CPU Torch is
selected from its official CPU index and constrained during the full resolution.
NVIDIA/CUDA/ROCm/Triton packages are rejected. Runtime metadata must show that
Torch was built without CUDA or HIP. A successful pip dependency check is required.

The Snowflake arctic-xs model is resolved to an exact repository commit using
native model metadata. Only bounded JSON/text/safetensors data is downloaded;
each file must match its LFS SHA-256 or Git blob identity. A small explicit list
of standard sentence-transformer modules is admitted. Global settings reference
that local verified snapshot with device=cpu. There are no external model/API
credentials, user profile, usage tracking or product AI service.

A fresh mirror holds at most 512 tracked source files/16 MiB, at most 1 MiB per
file. Tests and third-party source are excluded, and HIP files are explicitly
routed as C++. Source inventory, path, complete file digest, configuration,
provider artifact and model revision bind every actual search receipt.
Candidates must refer to that inventory and contain text present in live source;
the complete inventory is verified again after each search. The original
checkout remains unchanged. Neither an install log nor an index marker proves
search use: actual successful provider JSON and native response hashes are kept.

The job emits bounded routes for filesystem namespace/extent mutations,
transactional integrity/publication, GPU supervision/recovery, compression
selection and safe relocation. These are navigation hints, not findings or
permission to change a file without inspecting current source. A later commit
needs fresh binding or a refreshed job before another broad search.

The shared MCP registration, its configuration, index secrets and other tasks
are untouched. No local daemon or local embedding process is started.

## Resource and ownership bounds

The Linux process tree has a 3 GiB memory ceiling, no swap, two CPU equivalents,
256 tasks, nice 19, no core dumps and a 1200-second lifetime. Every subprocess
also has an explicit deadline. A fresh output below RUNNER_TEMP is required with
12 GiB initial free space and a 4 GiB reserve. Package downloads total at most
2 GiB; inspected wheel expansion totals at most 4 GiB. A wheel has at most
20,000 entries, all wheels together 100,000, a member at most 1 GiB, and no
traversal/link/special entries. Model data totals at most 256 MiB/24 files.
Failures preserve native diagnostics and stop dependent routing.

No wheel, model, venv or index database is published. Only bounded native
resolver/download/model/source/search receipts and logs are retained. All
installation and storage activity is confined to the disposable VM.

## AMD runtime deployment research

The reviewed hosted Crawl4AI lane now has a separate AMD source group for
current official Windows deployment, installation, requirements and component
support pages. Native URLs, statuses, failures, content/digests and provider
identity are retained. Every AMD capture must pass before dependent deployment
decisions. Search snippets only discover URLs and are not source evidence.

This does not implement private AMD runtime distribution, a protected driver
installer, live HIP dispatch or GPU benefit. Deployment must follow verified
vendor component-distribution rules rather than assuming every SDK/runtime
component may be bundled or installed privately. CPU operation and the owner's
no-host-execution boundary remain controlling.

Exact-commit execution and actual-search receipts are required before declaring
the routing restoration complete. Compiler/codec qualification and filesystem
feature completeness are separate.

The first isolated resolver attempt found a current Python 3.15 CPU Torch wheel
but could not resolve general dependencies using the CPU-only vendor index.
Candidate discovery therefore uses --no-deps; the separate complete resolution
uses the approved PyPI/CPU indexes and still verifies every selected wheel before
installation. No package was installed by that failed attempt.

The first AMD deployment URL under latest redirected into a 429 Cloudflare
challenge. Its failure capture is retained and is not evidence of deployment
permission. The published docs-7.2.0 URL is a separate normal public-source
attempt with the same robots/timeout/no-bypass controls; inspect the resulting
native capture before using its contents or claiming current-policy agreement.

The complete binary resolver then found no qualifying PyYAML wheel for Python
3.15. This is a binary-distribution limitation of this reviewed provider policy,
not proof that PyYAML source cannot run there. The semantic provider therefore
qualifies Python 3.14 separately; normal filesystem build tooling remains on
3.15. No source-build bypass, downgraded package pin or global installation is
used to conceal the failed compatibility attempt.

The docs-7.2.0 deployment URL returned HTTP 404 and was rejected despite matching
navigation text. Native AMD repository branch metadata identifies docs/7.2;
the corresponding public docs-7.2 route is the next source candidate. Earlier
challenge/404 captures remain evidence of those failures, never policy evidence.
