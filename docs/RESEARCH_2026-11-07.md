# FlitzFS engineering research and cross-repository review

**Research date:** 7 November 2026. **Status:** source review, not a Windows/AMD benchmark. Future changes require fresh verification of software versions and support statements. This document records three independent source-check rounds and decisions, not claims that the alternatives were deployed.

## Research round A — Windows filesystem and AMD GPU constraints

- WinFsp offers a C/C++ user-mode filesystem tutorial, API callbacks and testing strategy. Native Windows filesystem semantics are still complex; WinFsp explicitly does **not** support all NTFS-specific functionality, including paging files and the USN journal. Select a **read-only, disposable data-folder scope** before considering writable mounts or installing anything. Sources: https://winfsp.dev/doc/WinFsp-Tutorial/ ; https://winfsp.dev/doc/NTFS-Compatibility/ ; https://winfsp.dev/doc/WinFsp-Testing/
- AMD's Windows HIP SDK support table explicitly lists **Radeon RX 9070 XT / gfx1201** as supported, but a supported runtime does not imply that FlitzFS's GPU codecs have passed correctness, transfer-overhead or WDDM timeout testing. AMD's ROCm 10.1 driver notes are dated **5 October 2026**. Sources: https://rocm.docs.amd.com/projects/install-on-windows/en/develop/reference/system-requirements.html ; https://www.amd.com/en/resources/support-articles/release-notes/RN-RAD-ROCM-10-01.html
- GPU usage remains strictly optional until standalone synthetic-buffer tests and a correct CPU reader pass; no GPU initialization in the M1.5 code.

## Research round B — Compression and safe path access

- Zstandard's API documents that `ZSTD_d_windowLogMax` limits streaming mode, not one-shot decoding, and recommends checking frame lengths and bounding destination allocations. M1.5 now validates exactly one frame and declared content size on each Zstd chunk. Source: https://github.com/facebook/zstd/blob/dev/doc/zstd_manual.html
- Microsoft documents `CreateFileW` and `FILE_FLAG_OPEN_REPARSE_POINT`, which is applied to the input handle alongside a regular-file attribute check. POSIX uses `O_NOFOLLOW | O_NONBLOCK` and `fstat` on the opened descriptor to avoid symlink races and FIFO blocking. Both paths use read-only handles; this is not a guarantee against hostile parent-directory manipulation or content mutation through another handle. Source: https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew
- `ReadOnlyCatalog` presently accepts intentionally limited ASCII virtual paths (16 files, at most 16 components and 4 MiB of aggregate index metadata); it avoids introducing a potentially unsafe writable namespace before Windows runtime testing.

## Research round C — WinFsp integration, durability and CI provenance

- WinFsp's `Open`, `Read`, `ReadDirectory` and `GetFileInfo` interfaces have distinct semantics and concurrency considerations. The catalog is **only a testable backend**: no WinFsp driver, service, user-profile startup, or mount operation is included. Source: https://winfsp.dev/doc/WinFsp-API-winfsp.h/
- The Windows file I/O docs describe explicit `FlushFileBuffers` behavior. A footer or successful compression never substitutes for transactional mutable storage and carefully ordered flushes. Source: https://learn.microsoft.com/en-us/windows/win32/fileio/flushing-system-buffered-i-o-data-to-disk
- GitHub's secure-use guidance recommends pinning actions to their exact commit SHA and retaining least-privilege workflow permissions. M1.5 retains `contents: read` and pins `actions/checkout` to the documented v4.2.2 SHA. Source: https://docs.github.com/en/actions/reference/security/secure-use

## Research round D — concurrent WinFsp dispatcher and safe CPU scheduling

- WinFsp's public API permits multiple dispatcher threads. Its **fine-grained** guard protects namespace operations but does not automatically guard all independent file I/O; the **coarse** mode serializes all requests. This justifies a FlitzFS-owned **per-file read lock** around the mutable decoder cache and file position while preserving potential concurrency between different files. Source: https://winfsp.dev/doc/WinFsp-API-winfsp.h/
- A C++ data race in the read cache is undefined behavior; `std::mutex` supplies a happens-before relationship for protected regions. The M1.6 `ReadOnlyCatalog` read and verification paths share each file's lock. Direct `Reader` remains single-threaded, and catalog destruction/move must never overlap callbacks. Source: https://cppreference.com/cpp/language/multithread
- CPU/Windows tests cannot qualify a future WinFsp request scheduler. Keep the dispatcher disabled until a Windows-only, disposable mount and cancellation/timeout tests are explicitly designed; do not auto-start mount services or drivers on the maintainer's machine.

## Research round E — short reads and native callback contracts

- The native WinFsp `Read` callback receives a `FileContext`, `UINT64 Offset`, `ULONG Length`, buffer, and `PBytesTransferred`; it is the future adapter's responsibility to return a correct status and count. Source: https://winfsp.dev/doc/WinFsp-API-winfsp.h/
- Microsoft's synchronous `ReadFile` documentation describes returning zero bytes without error when a read reaches the end of the file. M1.7 models this **in a pure C++ projection only**, returning a short result across EOF or an empty result at/past EOF. This is **not** evidence that a WinFsp native callback is complete; NTSTATUS and lifetime semantics still require integration tests. Source: https://learn.microsoft.com/en-us/windows/win32/fileio/reading-from-and-writing-to-files
- The WinFsp tutorial's `Read`, `GetFileInfo`, and `ReadDirectory` examples confirm separate callback and metadata obligations. A high-level projection API is intentionally implemented without linking or loading the native WinFsp DLL, installing drivers, or touching system mount points. Source: https://winfsp.dev/doc/WinFsp-Tutorial/
